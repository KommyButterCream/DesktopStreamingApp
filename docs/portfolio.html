DesktopStreamingApp

이 시스템의 어려움은 개별 기술이 아니라 경계에 있었다. 캡처는 GPU 텍스처를 만들고, 인코더는 다른 GPU 디바이스에서 그걸 읽어야 하고, 전송은 그 결과를 여러 뷰어에게 복사 없이 뿌려야 하고, 디코더는 다시 텍스처로 되돌려야 한다. 각 경계마다 다른 도구가 필요하다.

그리고 어느 한 곳이 막히면 증상이 항상 다른 곳에서 나타난다 — "화면이 안 나온다" 는 캡처·인코딩·전송·디코딩 어디서든 나올 수 있다. 그래서 이 앱이 하는 일의 절반은 어느 단계가 막혔는지 구분할 수 있게 만드는 것이다.

왜 DLL 로 나눴나

모듈화 자체가 목적이 아니었다. 경계마다 이유가 따로 있다.

1. 재사용 대상이 실제로 있다

D3D11ImageView 와 IOCPNetworkEngine 은 이 시스템 전용이 아니다. 뷰어는 검사 장비 UI 에, 네트워크 엔진은 다른 서버에 들어간다. 스트리밍이 그 모듈들의 한 사용처이지 그 반대가 아니다.

2. 검증 단위를 나눌 수 있다

각 모듈이 자기 하네스를 따로 갖는다 — NvEncodeBench(회귀 18케이스), IOCPNetworkEngine/tools(23개), TestHost(뷰어). 엔진 전체 처리량으로는 어느 부품이 병목인지 가릴 수 없다. 실제로 IOCP 엔진에서 락프리 큐 두 개와 분산 수집 송신을 부품 벤치로 재고 기각했다.

3. 디바이스 경계가 이미 나뉘어 있다

캡처와 인코더는 서로 다른 D3D11 디바이스를 쓴다(뒤에 이유가 나온다). 같은 프로세스 안에서도 이미 자원이 분리돼 있으므로, 코드도 그 선을 따라 나누는 편이 경계를 흐리지 않는다.

4. ABI 경계가 설계를 강제한다

DLL 경계를 넘으려면 STL 타입을 헤더에 노출할 수 없고, 콜백은 함수 포인터여야 하고, 수명 규약을 문서로 적어야 한다. 귀찮지만 그 제약이 인터페이스를 단순하게 만든다.

NvCodec 의 _Impl pimpl 이 그 예다 — nvEncodeAPI.h 와 CUDA 헤더가 사용자 쪽으로 새지 않고, SDK 버전을 올려도 사용자 재컴파일을 강제하지 않는다.

나누지 않은 것도 있다

Service/ 계층은 DLL 이 아니라 앱과 같이 빌드되는 소스다. 스트리밍 프로토콜은 이 앱 전용이라 재사용 대상이 없고, 서버와 클라이언트가 같은 패킷 정의를 공유해야 하므로 헤더 하나로 두는 편이 안전하다.

경계를 긋는 기준은 "나눌 수 있는가" 가 아니라 "따로 검증하고 따로 배포할 이유가 있는가" 였다.

전체 파이프라인

화면 한 장이 서버 GPU 에서 뷰어 화면까지. 각 단계의 담당 모듈과 스레드.

한 프레임의 여정

  1. 캡처 (캡처 스레드)

    duplication 이 데스크톱 표면을 준다. 화면이 안 바뀌었으면 여기서 끝 — 복사도 발행도 하지 않는다. 바뀌었으면 4슬롯 풀 중 하나에 복사하고 최신 표식을 옮긴다.

  2. 중계 (캡처 스레드 → 앱)

    앱이 GetLatestFrameHandle() 로 slotId 를 받아 텍스처 포인터는 버리고 slotId 만 인코더 큐에 넣는다. 포인터는 캡처 디바이스 것이라 인코더가 쓸 수 없다.

  3. 인코딩 (엔코드 스레드)

    인코더가 slotId 로 자기가 초기화 때 열어 둔 공유 텍스처를 찾는다. keyed mutex 를 잡고 BGRA 로 복사한 뒤 즉시 놓는다 — 이후 NV12 변환과 NVENC 제출은 전부 인코더 디바이스 안의 일이다.

  4. 회수 (완료 스레드)

    완료 이벤트를 기다렸다 비트스트림을 꺼내고 슬롯을 먼저 반납한 뒤 앱 콜백을 부른다. 캡처 슬롯 반납도 이 경로로 돌아간다.

  5. 브로드캐스트 (완료 스레드)

    프레임을 32KB 청크로 자르고, 청크마다 SharedSendPacket 하나를 만들어 참조계수만 올리며 모든 뷰어 큐에 넣는다. 뷰어별로 전부-아니면-전무다.

  6. 수신·재조립 (IOCP 워커 → 스케줄러)

    클라이언트가 chunkIndex 순서를 검증하며 512KB 재조립 버퍼에 채운다. 하나라도 어긋나면 그 프레임을 통째로 버린다.

  7. 디코딩 (디코드 스레드)

    cuvidParseVideoData 안에서 콜백 셋이 동기로 돈다. 마지막 콜백이 CUDA 커널로 NV12→BGRA 변환 후 D3D11 텍스처에 쓰고 이벤트를 기록한다.

  8. 페이싱·표시 (디코드 스레드)

    프레임 순번으로 표시되어야 할 시각을 계산해 그때까지 기다렸다 뷰어에 공유 텍스처 핸들을 넘긴다. 뷰어는 자기 렌더 스레드에서 그린다.

모듈 간 데이터 전달

경계가 셋이고, 셋 다 다른 방법을 쓴다. 그 선택이 설계의 핵심이다.

경계무엇이 건너가나방법왜
캡처 → 인코더GPU 텍스처 (QHD BGRA ≈ 14 MB) KEYEDMUTEX 공유 텍스처 + slotId 디바이스가 달라 포인터를 넘길 수 없다. 복사하면 프레임당 14 MB
인코더 → 네트워크H.264 비트스트림 (≈ 42 KB) 콜백 + 참조계수 패킷 뷰어 N 명에게 같은 바이트를 보낸다. 복사는 한 번만
네트워크 → 디코더비트스트림 청크 버퍼 복사 수신 버퍼는 곧 재사용된다. 여기만 복사가 맞다
디코더 → 뷰어GPU 텍스처 공유 핸들 뷰어가 자기 엔진을 따로 쓴다

경계 1 — 왜 디바이스를 나눴는가

처음에는 캡처와 인코더가 같은 D3D11 디바이스를 썼다. 30fps 에서는 잘 돌았고 60fps 에서 수십 프레임 만에 캡처가 영구히 멈췄다. 스택 덤프로 잡은 교착이다: 

캡처   ProcessCaptureFrame → D3D11ImmediateContextGate::Enter
       → RtlAcquireSRWLockExclusive                    (영구 대기)

인코드 SubmitFrame → nvEncodeAPI64 → d3d11 → nvwgf2umx
       → WaitForSingleObjectEx                         (게이트 보유)

immediate context 를 지키는 게이트 하나를 두 스레드가 다퉜고, 인코더가 그걸 쥔 채 드라이버 안에서 무기한 블로킹했다. 캡처는 16ms 마다 그 게이트를 원하므로 통째로 죽었다.

락 규약을 다듬어서는 풀리지 않는 종류였다. 순환의 한 변이 드라이버 안에 있어서 우리가 그 대기를 놓아 줄 방법이 없다. 시도해서 아닌 것으로 확인한 것들 — 복사 완료 대기 켜기, 인코드 버퍼 4→8, nvEncEncodePicture 게이트 제거, NV12 변환 뒤 Flush. (nvEncMapInputResource 의 게이트를 빼면 프로세스가 죽는다)

그래서 게이트 공유 자체를 없앴다. 인코더에 별도 디바이스를 주고, 캡처 풀을 KEYEDMUTEX 공유 텍스처로 만들어 인코더 디바이스가 초기화 때 한 번 열어 둔다. 두 컨텍스트가 독립이므로 인코더가 드라이버 안에서 얼마나 오래 기다리든 캡처는 영향받지 않는다.

경계를 넘는 것은 slotId 하나뿐이다

앱은 NvEncInputFrame::texture 를 일부러 nullptr 로 둔다. 그 포인터는 캡처 디바이스의 것이고, 인코더는 sourceSlotId 로 자기가 미리 열어 둔 텍스처 4장 중 하나를 고른다.

매 프레임 OpenSharedResource1 을 부르는 것은 그 자체가 드라이버 왕복이다. 핸들을 한 번만 여는 것이 이 구조가 싼 이유다.

경계 2 — 청크 하나를 뷰어 N 명에게

뷰어가 8명이면 같은 32KB 를 8번 보내야 한다. 8번 복사할 이유는 없다. 

패킷 1개 생성 → SharedSendPacket::Create   참조계수 1 (배포자 몫)

for 뷰어 in 구독자:
    AddRef(packet)                            계수만 올린다
    viewer->EnqueueSharedSendPacket(packet, ReleaseCallback)
       실패하면 → Release(packet)              놓는 것은 호출부 몫

Release(packet)                               배포자 몫을 놓는다
// 마지막 뷰어의 송신이 끝나면 계수가 0 이 되고 블록이 풀로 돌아간다

경계 3 — 반납 경로가 역방향으로 흐른다

캡처 슬롯은 인코더가 다 쓴 뒤에 반납해야 한다. 그런데 인코더는 캡처를 모른다. 그래서 앱이 SetFrameReleaseCallback 으로 반납 훅을 걸어 둔다 — 인코더가 프레임을 다 썼거나 버렸을 때 그 콜백이 불리고, 앱이 캡처 슬롯을 돌려준다.

유입 큐가 latest-only 라 버려지는 경로가 정상이다. 반납을 성공 경로에만 걸어 두면 버려진 프레임의 캡처 슬롯이 영영 묶인다.

서버 앱의 조립

초기화 순서가 곧 의존 관계다. 그리고 그 순서를 틀리면 조용히 깨진다.

  1. D3D11 엔진 #1 (캡처용) · 게이트 켬

    캡처 엔진이 이 디바이스를 쓴다.

  2. 캡처 엔진 — SetFramePoolSharable(true) 를 Initialize 전에

    이게 구조의 출발점이다. 풀 텍스처가 KEYEDMUTEX 로 만들어진다. SetWaitForFrameCopyCompletion(false) 도 같이 끈다 — 복사 완료를 CPU 쿼리로 기다리는 대신 keyed mutex 가 그 순서를 맡는다. 드라이버가 아는 동기화라 더 정확하고 더 싸다.

  3. 캡처 이벤트 콜백 등록

    등록하지 않고 있던 시절이 있었다. 그래서 모니터 잠금·전체화면 전환·드라이버 갱신으로 캡처가 조용히 멈춰도 서버는 아무 일 없다는 듯 돌았고, 남는 증상은 "프레임이 안 온다" 뿐이었다.

  4. D3D11 엔진 #2 (인코더용) · 게이트 켬

    게이트는 이 디바이스에도 필요하다 — 엔코드 스레드와 완료 스레드가 같은 컨텍스트를 쓰기 때문이다. 다만 그 둘은 캡처와 무관하다.

  5. 인코더 생성 + 공유 풀 등록 + 콜백 4종

    비트스트림 · 오류 · IDR 질의 · 프레임 반납. 해상도가 바뀌면 이 단계만 다시 탄다.

  6. 스트림 정보 설정 → 서버 기동

    SetStreamInfo 가 StartServer 보다 먼저다 — 여기서 올린 버전이 구독 응답에 실려 나간다.

  7. 엔코드 스레드 → 캡처 스레드 순으로 시작

    소비자를 먼저 세운다. 반대로 하면 첫 프레임들이 갈 곳이 없다.

프레임률을 한 곳에서만 정한다

TARGET_FPS = 60 하나를 캡처(SetTargetFps), 인코더 (frameRateNumerator), 스트림 정보가 전부 쓴다. 예전에는 셋이 서로 다른 값을 들고 있었다 — 레이트 컨트롤이 기준으로 삼는 fps 와 실제 투입 속도가 다르면 비트레이트가 그만큼 어긋난다.

지터 버퍼 — 순번으로 표시 시각을 복원한다

60fps 면 프레임 간격이 16ms 다. 도착이 5ms 빨랐다 20ms 늦었다 하면 — 프레임을 하나도 잃지 않아도 — 사람 눈에는 끊김으로 보인다. 

목표시각 = 기준시각 + (순번 − 기준순번) × (1000/fps) + 16ms

timestamp 는 인코더가 넣은 프레임 순번이고 NVDEC 를 손상 없이 통과해 돌아온다. 서버 프레임 간격이 고정이니 순번만 있으면 표시 시각을 복원할 수 있다.

이르면 그만큼 자고, 늦었으면 그냥 표시한다. 기준이 100ms 이상 어긋나거나 250ms 이상 밀리면 기준을 다시 잡는다 — 없으면 한 번 밀린 만큼 영원히 밀린 채로 간다.

프로토콜

패킷 4종. 설정은 상수가 아니라 스트림 프로파일에서 계산한다.

패킷방향목적
SUBSCRIBE / UNSUBSCRIBEC → S 구독 시작/해지. 구독 응답에 스트림 정보 버전이 실린다
STREAM_INFOS → C 해상도 · fps · 코덱 · 버전 2종. 해상도가 바뀌면 다시 보낸다
FRAME_CHUNKS → C 유일한 가변 길이 패킷. frameId · chunkIndex/Count · offset · 페이로드
FEEDBACKC → S 수신 상태 증분 3종 + 보고 순번. 28바이트 · 초당 1회

패킷 크기가 uint16_t 인 것이 32KB 청크를 정했다

엔진의 PACKET_HEADER::packetSize 가 uint16_t 라 한 패킷이 65,535 바이트를 넘을 수 없다. 넘는 값을 적어 보내면 받는 쪽이 프로토콜 위반으로 보고 연결을 끊고, 보낸 쪽에는 원인 모를 피어 끊김만 남는다.

그래서 크기 계산 헬퍼가 uint16_t 를 돌려주고, 넘치면 0 을 돌려 호출부가 반드시 확인하게 만든다. 청크 32KB 는 그 안에서 고른 값이다. static_assert 로 전제를 코드에 박아 뒀다.

설정을 프로파일에서 계산한다

StreamProfile  fps 60 · bitrate 20 Mbps · peakFrameFactor 4 · backlogMs 100

평균 프레임    = 20,000,000 / 60 / 8      = 41.7 KB  → 2 청크
피크 프레임    = 41.7 KB × 4              = 167 KB      → 6 청크
백로그         = 20 Mbps × 100ms / 8      = 250 KB      → 8 청크
송신 큐 깊이   = max(피크, 백로그) + 여유 = 12 청크

예전에는 프로토콜 상한(512KB = 17청크)에서 잡았다. 실제 프레임은 2청크라 "4프레임 분량" 이라고 적어 둔 68엔트리가 실제로는 34프레임, 약 570ms 였다. 의도한 것의 8배를 붙들고 있었고, 그 8배는 전부 지연이다.

적응 제어

제어 루프 셋. 각각 다른 신호를 보고 다른 것을 조절한다.

1. 비트레이트 — 네 가지 혼잡 신호

congested = chunkFailDelta > 0      송신 큐에 안 들어감        (서버가 봄)
         || incompleteDelta > 0    프레임 통째로 포기         (서버가 봄)
         || discardDelta > 0       재조립 실패                (뷰어가 알려줌)
         || decodeDropDelta > 0    디코더가 못 따라감          (뷰어가 알려줌)

혼잡  → ×0.75  즉시
깨끗  → ×1.15  3구간 연속일 때만

내릴 때 빠르고 올릴 때 느린 것이 정석이다. 반대로 하면 경계에서 오르내리기를 반복하면서 화질이 계속 출렁인다.

forceIdr 은 false 다. 비트레이트만 바꾸는데 IDR 을 강제하면 그 프레임이 P 프레임의 몇 배가 되어 방금 줄이려던 혼잡을 악화시킨다.

뒤의 두 신호가 클라이언트 피드백에서만 나온다는 점이 중요하다. 링크가 멀쩡한데 뷰어 GPU 가 디코딩을 못 따라가는 경우, 서버 쪽에서는 완전히 조용하다.

2. 자가 치유 — 밀린 뷰어에게 IDR 을 요구하지 않는다

뷰어 하나가 프레임을 놓쳤다고 IDR 을 강제하면 그 프레임은 모든 뷰어가 받는다. 게다가 UltraLow 프리셋은 lowDelayKeyFrameScale = 1 이라 IDR 도 한 프레임 예산을 넘지 못한다 — 비트레이트가 튀는 대신 화질이 무너진다. 밀린 뷰어 하나가 전원의 화면을 깎는 구조고, 그 자체가 되먹임이다.

intra refresh 가 켜져 있으면 매 프레임 일부 띠가 intra 로 갱신되고 60프레임에 한 바퀴 돈다. 이미 화면을 갖고 있고 일부만 놓친 뷰어는 P 프레임만 받아도 복원된다.

실측 — 디코더 앞에 90프레임(1.5초) 공백을 5회 반복 주입: 오류 0, idr=0, 화면 정상 복귀

다만 쓸 화면이 아예 없는 뷰어(신규 구독 / 해상도 변경)는 다르다. 참조 프레임도 SPS/PPS 도 없어 refresh 파도로 복원될 것이 없다. 그쪽은 자가 치유와 무관하게 항상 IDR 을 요구한다 — 두 경로를 다른 함수로 갈랐다.

3. 지터 버퍼 — 도착 흔들림을 표시 시각으로 되돌린다

앞 절에 있다. 여기서는 셋의 관계만 — 비트레이트는 보낼 양을, 자가 치유는 무엇을 보낼지를, 지터 버퍼는 언제 보여줄지를 정한다. 셋 다 다른 층이라 서로 간섭하지 않는다.

::InterlockedExchange(&m_streamRebuildPending, TRUE);

// 실제 재생성은 앱 스레드의 ServiceStreamRebuild() 가 한다

재생성 상한을 둔 이유

인코더가 계속 실패하는 원인(드라이버 문제, VRAM 고갈)이 재생성으로 풀리지 않으면 무한 재생성 루프가 된다. 60초 창에 3회를 넘으면 멈추고 그 사실을 남긴다.

실측 — DebugFailNextOutputs(16) 으로 주입: 3회 복구 후 4회째 상한에서 정상 정지. 그 동안 클라이언트는 3,641 프레임을 드롭 없이 디코딩

테스트가 찾아낸 내 회귀

해상도 변경 경로를 실제로(2560×1440 → 1920×1080 → 복귀) 돌려 보니 BroadcastStreamInfo 가 자가 치유가 켜지면 단락되는 함수를 쓰고 있었다. 포맷이 바뀌었는데 IDR 을 요구하지 않는다는 뜻이다.

그런데 동작하는 것처럼 보였다 — 재생성된 인코더가 첫 프레임을 IDR 로 내보내기 때문이다. 우연히 가려진 결함이었고, 요구 경로를 별도 함수로 갈라 고쳤다.

기술보다 방법이 남았다

이 목록에서 반복되는 패턴이 셋 있다.

경계를 정하고 그 경계에 맞는 도구를 고른다 — GPU 간에는 공유 텍스처, 스레드 간에는 원자 연산, 프로세스 간에는 패킷. 하나로 덮으려 하면 어딘가 과하거나 모자라다.

재고 나서 판단한다 — 락프리 큐 두 개, 분산 수집 송신, 디스패치 스레드, 타일 워커 풀. 넷 다 재고 기각했다. 측정 없이 했다면 넷 다 구현했을 것이다.

실패의 등급을 나눈다 — 프레임 1장 유실과 세션 포기를 같은 코드로 다루면 복구 가능한 상황에서 죽거나 복구 불가능한 상황에서 조용히 얼어붙는다.

트레이드오프와 한계

고르지 않은 것들, 그리고 남은 것.

의도적으로 포기한 것

  • UDP / FEC — TCP 유니캐스트다. 손실 복구를 전송 계층에 맡기는 대신 재조립 실패를 그냥 프레임 폐기로 처리한다. LAN 을 전제한 선택이고, 인터넷 경로로 가려면 이 결정부터 바꿔야 한다.
  • 멀티캐스트 — 뷰어마다 같은 바이트를 따로 보낸다. 서버 송신량이 비트레이트 × 뷰어 수라 20 Mbps × 8 = 160 Mbps 로 기가비트 LAN 안에 든다. 뷰어가 수십이면 다시 봐야 한다.
  • 오디오 — 화면만 보낸다. 요구에 없었다.
  • H.265 / AV1 — H.264 고정. 코덱 선택을 설정으로 빼는 대신 한 코덱에서 VUI·GOP·VBV 를 정확히 맞추는 쪽에 시간을 썼다.

이번에 고친 것

  • 셰이더 경로를 DLL 자기 위치 기준으로 — 뷰어가 D3DReadFileToBlob(L"../Shaders/X.cso") 로 작업 디렉터리 기준 상대 경로를 넘기고 있었다. 그래서 누가 어느 폴더에서 실행했는가가 결과를 정했다 — 프로젝트 폴더에서 F5 로 띄우면 맞고, exe 를 자기 출력 폴더에서 실행하면 x64\Release\..\Shaders 를 보게 되어 초기화가 실패했다.
  • 증상이 "D3D11ImageView 초기화 실패" 한 줄뿐이라 원인과 거리가 멀었다. 실제로 이 세션에서 다른 변경을 검증하다 마주쳤고, git stash A/B 로 선행 문제임을 확인한 뒤에야 경로 문제로 좁혀졌다.
  • 이제 GetModuleHandleEx 로 이 DLL 의 위치를 찾아 그 기준으로 후보 셋 (Shaders\, ..\Shaders\, ..\..\Shaders\)을 순서대로 확인한다. 작업 디렉터리와 무관하고, 예전 경로도 마지막에 한 번 더 시도해 기존 호스트를 깨지 않는다. 출력 폴더 실행과 프로젝트 폴더 실행 양쪽에서 확인했다 — 각각 1,197 / 897 프레임 유실 0.

남아 있는 것

  • 클라이언트 쪽 게이트 경합 — 서버는 디바이스를 나눴지만 클라이언트는 디코더와 뷰어가 별도 엔진이면서도 렌더 부하가 커지면 같은 문제가 재현될 수 있다. 측정에서 렌더러 점유율 72% 일 때 인코드 지연이 4.8배까지 늘었다.
  • 셰이더 파일 배치가 솔루션마다 다르다 — 로딩 자체는 DLL 자기 위치 기준으로 고쳤지만(아래), Shaders/ 폴더가 솔루션 루트에 있는 배치와 DLL 옆에 있는 배치가 섞여 있다. 빌드 후 복사 단계를 넣어 DLL 옆 하나로 통일하는 것이 맞다.
  • 뷰어 수에 따른 비트레이트 자동 조정 없음 — 뷰어가 늘면 송신 총량이 비례해 늘지만 목표 비트레이트는 고정이다. 적응 제어가 혼잡을 보고 내리기는 하지만 사후 대응이다.
  • 재현되지 않은 종료 하나 — 원자 읽기 전환 검증 중 서버가 15초 만에 조용히 종료된 일이 있다(0x0000087d, KERNELBASE). A/B 와 3회 재실행으로 재현되지 않았고 변경과 연결 짓지 못했다. 기록으로 남겨 뒀다.

이 시스템에서 얻은 것

가장 크게 배운 것은 통합이 부품보다 어렵다는 점이다. 캡처도 인코딩도 전송도 각각은 동작했는데, 셋을 붙이자 60fps 에서 죽었다. 원인은 어느 모듈의 버그도 아니었고 두 모듈이 자원 하나를 공유한다는 사실이었다. 그런 문제는 모듈 안에서는 보이지 않고, 모듈 단위 테스트로도 잡히지 않는다.

그래서 이 앱 계층이 실제로 하는 일의 절반은 파이프라인 조립이 아니라 어느 단계가 막혔는지 구분할 수 있게 만드는 것이 됐다 — 단계별 카운터, 상태 표시, 장애 주입 훅. 만들 때는 부수적으로 보였는데 결과적으로 가장 많이 쓴 코드다.
